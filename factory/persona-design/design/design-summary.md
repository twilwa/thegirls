# A home for Red and Blue

I recommend giving Red and Blue separate OpenClaw homes, then building a small layer that preserves what each did, learned and chose. OpenClaw handles the hard practical work of waking up, talking across channels and choosing models. The new layer makes continuity portable and inspectable. It keeps original events and commitments, lets each persona write its own account of older experiences, and gives it a way to return to the original when a memory sounds wrong. The [research report](report.md) compares this with Connectome, Letta and OpenClaw alone and lists the sources. This is a design, not a claim that either persona is already running.

The owner wants more than two assistants that recite character sheets. Red should be able to follow an unexpected lead. Blue should be able to say that the lead is weak and explain why. Both should develop interests, remember corrections, keep promises, choose work during quiet periods and sometimes decide to do nothing. A short starting charter gives them different voices and values, but it does not freeze them. Changes to their tastes, routines and self-description leave a dated trail. Neither the charter nor their speech should imply a proven inner life. Anthropic's work on model character and drift is useful caution here: character is shaped by the underlying model as well as prompts, and model welfare is an open question, not a finding of consciousness. Sources and limits are in the report.

Each persona keeps an append-only history of events, conversations, decisions and promises. A recent stretch can stay verbatim; older stretches can be summarized in the persona's own voice. The summary points back to its source events and can be corrected without erasing them. When a session starts, the persona gets its charter, active goals, open promises, recent events and relevant older memories within a fixed context budget. A source-cited shared note can cross between Red and Blue; their private diaries and raw conversations cannot. If a summary contradicts its sources or drops a promise, the original events win. The hardest part is choosing what to remember, not storing more text. Before going live, we should replay past synthetic episodes and check whether compression changes a relationship or a commitment.

A bounded wake loop lets each persona revisit its own goals, budget and invitations. It may work, propose a new project, ask for help, or sleep. Quiet hours, task deadlines and spending limits constrain the loop. Temporary workers can investigate in parallel, but receive only the task and sources they need. An optional independent fleet might come later; neither persona gets the existing Firstmate fleet's command access as a birthright.

Red and Blue may choose from owner-approved models and routes and may propose changes to their prompts, memory habits and local tools. Every model choice records the reason, old and new model, provider route identity, cost and outcome. Separate provider keys or authorized, attributable routes are necessary, including for fallback, utility and child calls. If an existing subscription cannot identify and bill each persona separately under the provider's rules, we should not quietly share the owner's login. A persona can trial a change and roll it back. Executable code, new privileges, wider audiences and higher budgets need tests and human approval before activation. Rejected proposals still belong in its history.

The boundary must be real. Each persona needs its own non-root OS or container identity, gateway, storage and platform account. No mounts of Firstmate control files, fleet secrets, owner browser sessions or the other persona's private state. An external broker can carry a narrowly specified task or shared note, but not a credential or a fleet command. OpenClaw warns that a workspace is not a sandbox. A prompt telling Red not to look at Blue's files is not a substitute for a denied filesystem read.

**First build, Stage A.** Make a disposable offline simulation with synthetic conversations, fake models, a fake channel and a clock we can advance. It should show that two histories survive restart, summaries retain source links and promises, cross-persona and fleet-control reads fail at the mock policy, model calls get attributable log entries, quiet wakes stay quiet, and forbidden changes never activate. Leave test outputs and a deletion manifest. Stage A needs no root access, accounts, credentials, login, provider calls or approval to start. It proves the logic of these rules only. The later live stage must test OS isolation, actual connector behavior, model continuity and billing before any real secrets enter the homes.

Connectome is still worth a pilot: its history and first-person memory design fit this goal exceptionally well. But its host repository currently has no declared GitHub license or license file that I could find, despite the project's "open-source" description. Ask the maintainers before using its code. The other open risks are memory distortion, provider terms, platform privacy, cost leakage through fallback calls, and a persona that sounds consistent in a three-turn test but loses its bearings after a month. None is resolved by an impressive prompt. The report gives the checks and the precise requests main should make of the owner at each later stage.
