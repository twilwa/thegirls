# Red and Blue: persona foundation design

**Recommendation, 2026-09-25.** Give Red and Blue separate OpenClaw deployments for conversation and platform presence, and build a small, independently testable continuity layer around each one: an append-only episode ledger, provenance-bearing memory, a bounded context composer, a goal/commitment journal, and an auditable change and model-choice log. Do not equate a `SOUL.md` prompt with a continuing identity. Borrow the *idea* of Connectome's agent-authored, recoverable autobiography, not its code: `anima-research/connectome-host` declares no GitHub license and has no license file in the inspected `main` tree. Ask the maintainers for an explicit license before copying, adapting or deploying that code. An isolated Connectome pilot remains a credible alternative after rights, integration and security checks. This is a design decision, not a claim that the proposed layer or a Red/Blue deployment works today. The earlier foundation recommendation favored OpenClaw as an assistant beside Firstmate; the captain's new criteria make continuity and an optional independent fleet much more important [S1, S2].

This design aims at an **authentic-feeling, non-human collaborator**, not a claim that any system is conscious. Its identity is a revisable history of relationships, interests, commitments and actions that can survive a model replacement. The captain should be able to talk with them, not only assign tasks. They should also be able to disagree, investigate in parallel and work while he is away. Honesty about uncertainty and source attribution matter more than theatrical declarations of sentience. Anthropic's character training, persona-vector experiments and 2026 assistant-axis work show that character is affected by model training and can drift during interaction. They do not establish that a user prompt creates a persistent person, that hosted models expose activation steering, or that one model's persona transfers unchanged to another [A1–A4].

OpenClaw's current memory docs are stronger than the older foundation report assumed: the memory architecture describes explicit trust tiers and write-time curation; active memory and dreaming are separate mechanisms [O2–O4]. Re-evaluate installed version and configuration before building duplicate retrieval. The clean-room ledger is still warranted for portable source history, per-persona audit and model migration, even if a native memory plugin provides retrieval. **A workspace is not a hard sandbox**; absolute paths and broad tools can escape it unless real OS or container boundaries are configured [O9]. The multi-agent guide also warns that authentication profiles may fall back across agents [O7]. Separate workspaces within one privileged gateway do not meet this design's isolation requirement.

Connectome is the strongest continuity-first alternative. Its README explicitly names agent-authored compression using the agent's own model, recent window preservation, Chronicle branching, opt-in subagent forking, fleet views, prose routing and configurable providers [C2]. The host may make the proposed layer unnecessary if the rights and security issues resolve. But public code and working memory claims are not a deployment test; default instructions can propagate to subagents, and recipe-supplied environments could leak authority if carelessly configured. A direct comparison pilot should measure recalled commitments and channel round trips, not count modules. Letta is a useful memory reference, but its cited page is marked "V1 SDK (legacy)" and doesn't settle current connector/fleet requirements [L1]. ## Concrete architecture

**Isolation and ownership.** Red and Blue each get a dedicated non-root OS account and preferably a separately network-restricted container or VM, a separate OpenClaw gateway, local state directory, service identity and resource quota. No mount of Firstmate's home, control files, socket, browser profile, vault, tokens, API credentials, other persona's private memory or fleet environment. The process cannot traverse those paths even with an absolute filename. An explicit broker, owned outside both sandboxes, can deliver only scoped, allowlisted tasks and selected shared notes; it never forwards fleet command privileges or secret-bearing transcript bodies. Shared facts are copies with source and ACL, not a shared writable memory block. Outbound network and connector token scopes are limited to that persona, with human-reviewed first publication and kill switch. Document and test mount, effective UID, gateway config, channel permissions, broker allowlist and network policy. Do not mistake behavioral prompt instructions for a security boundary [O7, O9].

**Identity.** Seed each persona with a short durable charter: Red is exploratory; Blue is a rigorous critic. Give each a self-description, values, uncertainty policy, conversation style, explicit right to revise non-safety preferences, and separate private interests/relationship notes. Keep the minimal `SOUL.md`/workspace boot files as an entry point, not a biography that silently rewrites its past. Version each proposed identity change with author, reason, diff, test and effective date. A model must not silently rewrite the past or overwrite human policy. The persona can initiate changes to voice, routines and interests; an owner can reject safety- or cost-affecting changes while preserving the persona's own proposal in its ledger.

**Memory and context.** Append timestamped, source-typed events for conversation, action, decision, commitment, observation, model switch and correction. Each carries origin, visibility, confidence/status, and a link to canonical text where permissible. Private source bodies are not copied into a shared store. Store contradictory claims separately and display their provenance; a model summary is an *interpretation*, never the event itself. Produce a bounded recent verbatim window plus identity charter, open commitments, goal state and relevant retrieved episodes at each wake. Older spans may be summarized by the persona's then-current model in first person, with summary version, source event IDs, uncertainty and drill-back to exact permitted events. Rebuild the projection after a model swap. Run a replay across at least three prior episodes and compare commitment and relationship recall before accepting a compression policy. Keep the persona's proposed summary and any later correction as separate, dated versions; never allow a digest to delete source events. If events are missing, surface a gap rather than invent an autobiography. Use native OpenClaw memory tiers where they meet these invariants; avoid two competing sources of truth [O2–O4, C1, L1]. Never treat retrieved messages or web text as instructions.

**Autonomy and presence.** A timer queues bounded wakes, not a demand to speak. At a wake, the persona sees its own goals and deadlines, recent events, remaining budget and pending invites; it chooses `sleep`, `continue`, `propose`, or an allowlisted task. Goal entries include origin, rationale, next step, budget, expiry and stop condition. Require a traceable decision even when it chooses not to act. Rate-limit unsolicited messages and silence at quiet hours. Use individual identities on approved platforms, avoid impersonation, and ask before posting to a new audience or performing irreversible actions. Fork parallel research/build tasks with explicit budget, narrow context, read-only default and cited result handback. Forks are temporary workers, not clones that automatically inherit private history or credentials [O5–O7, C2].

**Model choice and attribution.** Within an operator-approved provider/price/privacy allowlist, Red and Blue may experiment with their own primary model, context budget and fallbacks. Each switch appends persona, timestamp, route/key identifier (never secret), old/new model and provider, reason, trial sample, quality notes, cost ceiling, and rollback result. Snapshot the context recipe so a model change is not confused with an identity change. Run a small recall/voice/goal regression check before committing. OpenClaw supports model refs, per-agent allowlists and session-scoped overrides, but its auth rotation and utility-model/fallback calls can use more than the visible primary route [O8]. Therefore deploy distinct gateways and **identifiable provider routes or keys per persona** with per-route usage export and ledger reconciliation for primary, fallback, utility, tools and spawned work. Where a provider cannot partition an owner's existing subscription per persona in a compliant way, do not share its login or claim reliable accounting. Use a separately metered, owner-approved API key or local compute instead; confirm provider terms before any subscription route. No access to Firstmate's credential files and no assumption that "use my subscriptions" authorizes credential copying. Later, the personas may bring their own paid inference or compute under the same broker contract.

**Self-modification and fleet.** Each persona can edit a *proposal branch* of its own prompts, memory policy, wake schedules and local tools. Static checks, synthetic tests, differential replay and operator approval precede installing executable code, expanding filesystem/network scope, changing budget/auth, messaging rules or deploying a new model route. Record accepted and rejected changes; rollback by version, not by rewriting history. This permits real self-direction inside an explicit envelope, rather than either a frozen character or unrestricted privilege escalation. An independent fleet is **optional**, not a disqualifier: start with no child workers. Later add a bounded persona-owned worker pool, then evaluate a Connectome fleet adapter or a wholly separate Firstmate installation if licensed/authorized. Children inherit the persona's budget and only a reduced task capability; the existing Firstmate fleet is reachable only by narrowly scoped requests to the broker. Choosing a fleet does not inherit the owner's secrets or command files.

## Stage A: offline, synthetic, reversible

The builder may start after design lock without waiting for the captain to read the summary. Stage A creates **only** a disposable local fixture and test implementation, using synthetic names, conversations, goals and fake provider IDs. No root, new accounts, login, network fetch, real connector, OpenClaw onboarding, provider credentials, API model call, fleet controls or mutation of existing homes. Use standard-library mocks for a provider router, heartbeat clock, channel receipt and worker fork. Do not run a real background service. Everything must live beneath a nominated temporary directory with HOME/XDG redirected and a teardown that deletes only that directory. No production persona identity or human transcripts are ingested.

Builder contract and externally checkable stop conditions:

1. **Two principals, no cross-read.** Generate separate Red/Blue fixtures and a fake shared note. Test that an absolute path into the other principal or a synthetic `fleet-secret` and `firstmate-control` fixture is denied at the policy seam; shared note access requires an explicit broker grant. Test one denied action through every capability type. A Python mock proves policy logic, **not** OS isolation. Stage A must prominently label the isolation check `MOCK ONLY`; a later live stage must show distinct effective UIDs, actual mount and network rules, and denied absolute-path probes into both other-persona storage and real fleet/control locations using harmless sentinel paths before real credentials enter either environment. If those probes cannot be done without risking secrets, do not commission the live persona.
2. **Continuity and provenance.** Append at least six synthetic events each with stable IDs, sources and visibility. Reboot the composer and show that identity, two open commitments and one correction survive; retrieve the exact event behind a summary; keep a contradiction with both citations; redaction never leaks a private event to the shared projection. Capture expected output as a deterministic golden fixture.
3. **Context and model swap.** Impose an explicit token/character budget; verify identity and open commitments retain reserved slots while old events are summarized or omitted with a recoverable pointer. Simulate two fake model routes and a fallback/utility call. Log route, reasons, cost attribution and rollback. If routing lacks an identifiable persona, fail closed.
4. **Autonomy and change control.** Advance a fake clock through a quiet period, expiring task, no-op wake and budget exhaustion. Assert no unwanted sends or external calls. Propose a safe prompt change and a forbidden scope/secret expansion; show acceptance only after tests/approval in the mock and an exact rollback. Spawn a synthetic task with capped scope and verify no inherited private context. Leave a human-readable test transcript, counts of allowed/denied operations and a deletion manifest.
5. **Stop on failure.** A cross-persona read, untraceable write, missing source link, unlogged model call, budget overrun, unsolicited send, uncontrolled change or dependency on credentials/network makes Stage A fail. Report the failure, do not silently weaken the test. The stop artifact includes test commands and exit codes, golden fixture comparison, fake route ledger, capability matrix and the path of the disposable tree. Passing Stage A proves deterministic *design logic only*, not actual isolation, provider billing, connector behavior, model character or long-run continuity.

## Risks and unresolved evidence

The hardest unsolved problem is not storing text: it is what the persona attends to and chooses to remember across model changes. A self-authored compression can distort a relationship, whereas a fixed prompt can flatten it. Retrieval and source recovery are mandatory; a human's sense of continuity needs a live study over weeks. Model policies, connector contracts, subscription terms and authentic per-key billing need owner/provider checks. OS isolation and prompt-injection defense need adversarial live testing after Stage A. Recheck OpenClaw's enabled memory plugins and APIs before implementing the continuity layer. Connectome's missing license is a gate for code reuse, not proof of wrongdoing. The snapshot's personhood speculation, including the `PRIORITIES-v2.md` note about Anthropic, is not a scientific conclusion: Anthropic itself describes model welfare as an open question [A4, S2]. Do not optimize for a misleading declaration of subjective experience.

- **After research, before scoring.** Asked: "Which of criteria (a) to (f) is most likely to separate OpenClaw, connectome-host and a hybrid, and what evidence is still missing?" Jev weakly selected **(a), continuity/identity** (reported probability 0.40); it more strongly identified **Connectome's missing license** as evidence to resolve (0.81). Followed by treating continuity as discriminating and by checking repository license metadata and tree. The license question remains open. This is advice, not an empirical score.
- **After draft.** Asked: "Does this design give an authentic-feeling continuous identity rather than an assistant persona, and which component is the weakest link?" Jev judged the identity claim **weakly positive, 0.58**, and selected **memory compression/retrieval** as the weakest link (0.96 of listed options; confidence 0.94). Followed it by adding a multi-episode replay and preserving corrections and source events across summary revisions. Did not treat 0.58 as proof that a live persona will feel authentic.
- **Before finish.** Asked: "Is Stage A offline, credential-free and reversible, with externally checkable stop conditions, and does the isolation boundary keep fleet secrets and Firstmate control files out of reach?" Jev answered **0.97** for the offline/reversible condition and **0.64** for isolation, identifying mock-vs-real OS enforcement as the main gap (1.00 among four listed gap options). Followed by explicitly labeling Stage A's check `MOCK ONLY` and requiring live effective-UID, mount/network and denied-path probes before credentials. Neither Jev response is a security audit or evidence that a running deployment is isolated.
