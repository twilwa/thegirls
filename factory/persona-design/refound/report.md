# Red and Blue: reopening the foundation choice

**What changed:** aligned the Astra subscription start, persona-owned GPT-or-OpenRouter choice, Claude Code advisor boundary and supported OpenClaw channel/task model routing.

**Recommendation, 2026-09-25.** Keep separate OpenClaw deployments for Red and Blue, but change what "OpenClaw-based" means. Let each persona own a replaceable context engine and memory implementation, backed by its own source-preserving episode ledger; use OpenClaw for delivery, wakes, model routing and the surrounding plugin ecosystem. Prototype this split with fake channels and models first. Do not grant either persona permission to update its live gateway just because plugins can be installed at runtime. The decisive merit is the combination of real platform presence with *documented* exclusive context and memory extension points, not Connectome's missing license. Pi is the strongest alternative for owning the whole runtime; Connectome is the best native continuity design. Neither yet offers this combination of ready-made human channels, bounded wakes and replaceable context without a substantial integration project. This is a conditional choice: if a synthetic turn cannot bypass unwanted OpenClaw context injection or maintain an idempotent source-preserving turn history, test Pi as the primary host rather than layering more hidden state on top.

This revises the locked [report](../design/report.md) and [design summary](../design/design-summary.md). It does **not** mean Red or Blue are deployed, or that OpenClaw's published SDK has been exercised on this machine. Connectome is treated as usable in principle, assuming an MIT answer to [the already-open licensing question](https://github.com/anima-research/connectome-host/issues/146). Permission must still be resolved before copying its code; that administrative question did not decide the ranking.

## OpenClaw 2.0 against the installed 2026.9.6

"OpenClaw 2.0" is the project's name for **v2026.8.1**, not an unreleased successor to installed v2026.9.6. Its release notes describe SQLite sessions/transcripts, built-in Memory, plugin installation and discovery, broader native apps and messaging, scheduling, provider controls and security approvals [1]. The published v2026.9.5 notes already include live plugin installation without a gateway restart. v2026.9.6 adds recovery for unfinished work after restart, 30-day Usage reporting, new models and further plugin/memory and compaction reliability work; it is an incremental update, not the arrival of 2.0 after 9.5 [2]. We inspected the published docs, not this host's installed plugin registry or settings. Do **not** attribute a particular SDK feature's introduction to 9.6 from a current docs page alone.

The plugin ecosystem matters more than the brand name. The [memory/context SDK](https://docs.openclaw.ai/plugins/sdk-overview/memory-and-context) exposes `registerContextEngine(id, factory)` and `registerMemoryCapability(capability)`, each with one active implementation. Durable admitted turns require a declared turn fence and atomic, idempotent `commitTurn` keyed by `advancementKey`; without the contract the host takes the legacy context path for that whole turn. A memory capability can run its own hooks, but session-transcript search results must pass its authorization hook or the host withholds those hits. These are substantive replacement seams, not just a different `SOUL.md`. They do **not** replace gateway routing, scheduler, auth, core tool policy, all prompt/session preparation or OS permissions. The [agent-harness SDK](https://docs.openclaw.ai/plugins/sdk-agent-harness) explicitly calls third-party installation experimental and reserves core-owned policy and session handling. A Pi harness underneath OpenClaw is plausible to investigate, not an established way to turn OpenClaw into a dumb connector.

Thus the owner gets material to inspect and change inside a large ecosystem, but less freedom than in a Pi-owned host. The test is whether the persona's composer determines the final effective prompt and can recover accepted turns exactly once. If core bootstrap/state competes with that contract, drop the proposed combination. Do not conceal duplicate context behind another plugin.

## Why someone moved to goated

The captain reported asking an agent who had moved from OpenClaw to [goated](https://github.com/Endgame-Labs/goated). That agent's account or exact words were not available in the supplied inputs or the public pages inspected. The goated maintainer's [migration guide](https://github.com/Endgame-Labs/goated/blob/main/docs/OPENCLAW_MIGRATION.md) says *its* motivation was repeated context injection/token cost, growing daemon memory, compaction losing important information and identity drift. It cites 3K–14K forced tokens per message and 1.9 GB after 13 hours, reaching 28 GB by day three; we did not reproduce these figures or establish the OpenClaw version/configuration involved. The guide also claims OpenClaw had no subagents, which contradicts current OpenClaw multi-agent documentation. Do not repeat that claim as a present-day fact. goated avoids owning the context window by handing it to Claude Code or Codex. At the inspected commit `39d94b98de0d39967ecd08be2514d87d1f3b1d43`, it launches Claude Code as a CLI subprocess; the audited paths include `--dangerously-skip-permissions` and a Sonnet fallback, while its security documentation says credential guardrails are not a formal sandbox. This is not an acceptable persona boundary or route to reuse here: it conflicts with the no-Sonnet rule and bypasses Claude Code's permission checks. That is a persuasive reason to *test for duplicate host context and recoverability*, not evidence that the particular migrating agent gave that explanation or that current OpenClaw still exhibits those measurements. Its [Pi runtime notes](https://github.com/Endgame-Labs/goated/blob/main/docs/PI_RUNTIME.md) call Pi headless support "working but still maturing" and say context estimate and compaction are not exposed. goated plus Pi is a useful controlled experiment, not today's default for a persona whose own context is a priority.

## Model choice and routing

Red and Blue both start on GPT-6 Astra through OpenAI Codex subscription authentication. Pi lists the exact subscription-catalog model `openai-codex/gpt-6-astra` (272K context, 128K maximum output); OpenClaw's canonical provider/model ref is `openai/gpt-6-astra`. The installed OpenClaw 2026.9.6 OpenAI setup docs support Astra through Codex subscription OAuth without Platform API billing. To preserve the chosen OpenClaw turn-composition layer, use the model-scoped `agents.defaults.models["openai/gpt-6-astra"].agentRuntime.id: "openclaw"`; the documented route uses OpenClaw's embedded runtime with the selected OpenAI OAuth profile and its internal Codex-auth transport, rather than the native Codex app-server harness. The implementation must select only the approved subscription OAuth profile under `auth.order.openai` and omit any Platform API-key profile, secret or `OPENAI_API_KEY` fallback. Otherwise an explicit OpenClaw runtime may select an API-key route when both credential kinds are eligible. This is a verified supported design route, not a configured login: no gateway start, authentication, live configuration change or OpenAI model call occurred.

After Astra, each persona makes her own first model decision: stay on subscription GPT models or choose an OpenRouter model funded by the owner's promo credits until they run out. Her choice log records model, route, budget/credit basis, reasons and observed effects. At 2026-09-25 05:47 UTC, `quota-axi` reported 61% remaining in the shared Codex window (established confidence), not a per-persona allocation or per-call price. Pi also lists `openrouter/openai/gpt-6-astra` (1.1M context, 128K output), but OpenRouter authentication was unavailable and the credit balance remains unverified. No new Fable work or Sonnet use is proposed; whether persona choice is exempt from the owner's factory rules remains his open question and is not decided here.

OpenClaw supports model routing by channel and task, but not multi-model voting. `channels.modelByChannel` pins channel IDs or DM peer IDs to `provider/model`, except where a session already has an active model override. Per-agent primaries use `agents.defaults.model` / `agents.entries.*.model`; purpose-specific slots include `agents.defaults.utilityModel`, `imageModel`, `pdfModel` and `mediaModels`, with per-agent overrides. These support an ensemble of model assignments across interactions, not a turn-voting ensemble. Exercise the intended mappings in Stage A before any live use. Claude remains external-advisor-only through the owner-run, bounded, text-only Opus broker running Claude Code; it is not a day-to-day model. OpenClaw `attach` can attach Claude Code to a gateway session with scoped MCP tools, but it is unnecessary for day-to-day turns and is not part of this design. The broker is not provisioned and requires owner approval; no persona files, operating authority or fleet credentials cross into it.

## Ownership, safety and what changes

Keep the locked design's append-only events, source-linked summaries, promise/goal journal, reversible character changes, Red/Blue private state and narrowly sourced shared notes. Connectome shows why a first-person summary is appealing; neither its compression nor OpenClaw Memory alone guarantees accurate recall. The persona may author a new version of its memory/context plugin and select an allowed model for experiments. Every proposal records the diff, purpose, test result and rollback point. A separately privileged builder/reviewer applies executable changes after tests and human approval for new privilege, audience or spend. The persona never has its own production plugin directory, service files or deployment credentials writable inside its sandbox. Pi extensions and goated's YOLO defaults are not permission boundaries; Connectome's editable instructions are not one either. If a full self-updating host is later desired, use disposable sandboxes and a signed promotion path, not a root-capable agent rewriting itself live.

The code path differs by candidate. On plain OpenClaw a persona can draft a plugin or workspace change, but gateway core changes stay operator-owned; on the chosen hybrid it authors the context and memory plugins plus ledger policies, then a reviewer promotes a tested artifact without granting gateway write access. On Connectome it can edit its recipe and instruction workspace and propose Chronicle/compression/host code patches in a separate checkout; a reviewer stages the executable host and checks that changed memory readers cannot cross principals. On goated it can change its private `workspace/self` and propose Go daemon or runtime-adapter patches, but a separate deployer must build/restart the daemon and constrain shell and token privileges rather than rely on default YOLO mode. On Pi it can author extensions and the context composer or propose a host fork, but extensions inherit the host's filesystem and process authority, so sandboxed test processes and separately approved releases are mandatory. Pi plus an OpenClaw bridge needs two reviewed artifacts and a narrow authenticated channel interface that cannot forward arbitrary tool calls or accept foreign session state. None of these write paths grants a persona the right to widen its own OS identity, budgets or channel audience.

Preserve **separate non-root OS identities or containers/VMs**, storage and channel accounts for Red and Blue. No Firstmate control files, fleet credentials, browser sessions or cross-persona raw conversations inside either environment. An external broker may pass a specific sourced shared note or task, never unrestricted fleet commands. Provider traffic needs a separately attributable route/key per persona wherever supported, including fallback, utility, worker and retrieval calls. Model-switch entries record old/new model, reason, route, cost and observed outcome. A subscription without compliant separable identity needs an owner-authorized route, not a copied fleet login. Optional fleets belong to the persona's bounded resources; Connectome's native fleet makes that alternative attractive, not disqualifying. These safety and attribution contracts remain regardless of host.

Stage A remains **offline, synthetic, disposable and credential-free**. Continue the foundation-independent fake clock, two isolated histories, mock cross-persona denials, source-preserving compaction/recovery, promise checks, quiet wakes, model/cost routing ledger, rejected unsafe changes and deletion manifest now. Add adapter contract tests: accepted-turn replay after crash is idempotent, memory search respects each requester, context budgets do not silently inject duplicate bootstraps, model switches cannot lose obligations, and candidate code changes cannot write the active runtime. Foundation-specific OpenClaw tests, still without provider calls, should load the published plugin interface in a disposable HOME, inspect composed turns, legacy fallback behavior, channel mocks, the `channels.modelByChannel` precedence rule, per-agent/task-purpose model slots and memory authorization. Pi/goated fallback tests should check session ownership, compaction visibility and a fake connector handoff; Connectome pilot should check Chronicle reconciliation, first-person summary source recovery, permissions and wake events. No such trial has yet run. Only a later isolated live stage can validate actual connector routing, billing, provider terms and OS-denied reads.

The later owner asks do not change: a separate OS/container identity if it needs root; authorized per-persona platform accounts and compliant provider routes/keys if login is needed; higher budgets or privileges for production activation. Do not ask for those to run Stage A. The licensing question at [connectome-host issue 146](https://github.com/anima-research/connectome-host/issues/146) still needs an answer before use of that code; it is not a request to block design or the clean-room prototype. If the slot test fails, make an explicit architecture decision between Pi plus a measured connector bridge and Connectome plus connectors, rather than silently growing the OpenClaw plugin.

## Advisory checkpoints and evidence limits

For the model-route revision, Jev was asked: "Does the revised design start both personas on subscription Astra without API billing, leave the stay-or-OpenRouter decision to each persona, and keep Claude as advisor-only through Claude Code?" It affirmed the design (probability 0.95; `typesafe/jev-1.13-20260917`, OpenRouter). I followed the verdict in the design. This is advisory review, not route validation or a security test.

Before scoring I asked Jev which host best supports continuous existence out of the box, which grants greatest autonomy over its own code and context, and what missing evidence matters most. It chose **OpenClaw** for existing continuity (0.68), **Pi** for code autonomy (0.70), and the missing **migrating agent's own testimony** (0.68), with respective confidence 0.59, 0.61 and 0.57. I followed the autonomy warning and explicitly marked the testimony unavailable; I did not treat its out-of-box continuity preference as proof of source-preserving identity. For the complete set, a subsequent `jev-cli find` pass with the six candidates ranked continuity as OpenClaw alone (0.56), chosen hybrid (0.17), Connectome (0.13), goated (0.06), Pi/bridge (0.06), Pi alone (0.02), but said **no adequate candidate** (`exists=0.26`). It ranked code autonomy as chosen hybrid (0.46), Pi/bridge (0.40), Pi alone (0.14), others near zero, with only a **partial** match (`exists=0.45`). I did **not** follow either full-list order: a relevance rank of short feature blurbs is not a validated identity or autonomy test and reverses Pi's documented full-runtime control. On documented merit, Connectome leads ready first-person continuity mechanisms; the hybrid's ledger could exceed it if tested. Pi leads full-host autonomy, then a Pi/bridge, then the chosen hybrid. The gaps are month-scale promise recovery, actual composed-turn control, authenticated channel bridging and the particular migrating agent's testimony. The final Jev question was: "Is this recommendation driven primarily by comparative merit instead of Connectome licensing, and which heavily weighted criterion is it weakest on?" With the comparative evidence and MIT assumption in the state, Jev returned **yes** (0.80) and **platform presence** as the weakest criterion (0.69 among four alternatives; confidence 0.60; model `typesafe/jev-1.13-20260917`, OpenRouter, 570 input and 67 output tokens). I followed the merit verdict, but **did not follow** its presence ranking: among these choices OpenClaw has the best documented ready-made channels and wakes; autonomy over the *whole host*, with policy and turn preparation still core-owned, is the chosen hybrid's weakest point. The unanswered question is whether its exclusive slots control the effective composed turn. Jev is an advisory opinion, not a test or source.
