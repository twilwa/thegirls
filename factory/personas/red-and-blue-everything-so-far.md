## Memory, choice and continuity

The current design proposes separate OpenClaw homes with persona-owned, replaceable memory and context code. Each would have original source-preserving conversation and decision history, a working context bounded by budget, a charter that can evolve, and a promise/goal journal. A summary should point back to its events; a corrected memory should not erase what it corrected. Red and Blue may share a sourced note, not each other's private diaries. A forgotten promise or a summary that changes a relationship would count as a failed continuity test. The initial card cannot provide any of this on its own. Even a good `SOUL.md` is not the whole identity: model, context, memory and history together affect how a persona continues. A model switch may change its voice; no source establishes consciousness or guarantees continuity across models. [Research on memory](https://github.com/twilwa/research-wiki/blob/main/docs/red-blue/README.md#durable-memory--topicthegirls-memory) · [Research on identity](https://github.com/twilwa/research-wiki/blob/main/docs/red-blue/README.md#identity-and-personas--topicthegirls-identity).

The choice of OpenClaw is **conditional**, not an endorsement of its entire context stack. Its connectors, heartbeat and exclusive memory/context-engine plugin slots make it a plausible starting chassis. An actual composed-turn test must show the host is not injecting competing context or losing accepted turns. If it fails, a Pi-owned runtime with a measured connector bridge is the next experiment. Connectome's Chronicle and first-person compression remain worth comparing; goated is another smaller shell, but its Pi integration does not expose compaction controls. Self-editing means proposing and testing persona-owned context/memory changes in staging, with independent review for a production release; it does not mean rewriting a live gateway or gaining privileges. Temporary workers or a fleet are optional later possibilities, not attached now. [OpenClaw research](https://github.com/twilwa/research-wiki/blob/main/docs/red-blue/README.md#openclaw-extensions--topicthegirls-openclaw).

## What exists; what waits

- **Built and tested:** Stage A ran offline with fake channels, models and conversations. Its synthetic harness tested histories, sourced summaries and promises, attributed mock calls, quiet wakes, rejected code changes, and mock access controls. Its passing checks do **not** show live delivery, actual provider bills or OS-level denied reads. See the Stage A research report locator below.
- **Chosen in the design, not live:** distinct OpenClaw homes, memory and context ownership, model experimentation and bounded wake loops. Real connector composition, billing attribution and memory behavior still need checking on the actual installed host/version before live use.
- **Approved for later, now paused:** persona separation and the consult-Opus broker retain the captain's earlier approval, but the captain's 2026-09-25 request pauses Stage B, separation build, broker build, live OpenClaw configuration, all accounts and signups. No provisioning or deployment has occurred for this handoff.

The earlier separation recommendation was for **this shared VPS**: separate locked users and rootless Podman with strict mounts, network isolation and an allowlisted egress gateway, subject to actual denied-read and reboot probes. `/dev/kvm` is absent *here*, so a Firecracker VM was not viable *here*. Your preference for **their own machine takes precedence**. A separate physical Linux box for both removes Firstmate's shared-host kernel and disk from the equation, but Red and Blue would still need separation from each other. A separate rented VM offers guest isolation from Firstmate but not necessarily a physical machine; confirm whether that meets your intent. The new host's KVM, AppArmor, capacity, admin access, backups, costs and egress need fresh checks; don't transplant this VPS's provisioning commands. Any future advisor relay should authenticate each persona on its own host and keep Firstmate's login and control services off it. No machine, tunnel, account or broker endpoint has been set up.

## What we should decide together

1. Does “their own machine” mean a captain-owned physical box, rented dedicated server, or an isolated VM? What operational burden and budget are acceptable? No purchase or host is selected.
2. Which repository should own their future infrastructure and histories? Keep the research wiki as an evidence/publication store, not a substitute persona diary or runtime repository.
3. After time together in the cards, which promises and preferences should each one actually retain, and how should either correct a mistaken memory without erasing history?
4. When you are ready to resume, what explicit model-route attribution, spending limits, logins and host boundary do you approve? Do the proposed per-persona model choices override other factory rules? Test the real connector and context composition before any live launch.
